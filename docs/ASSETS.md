# Asset provenance

Every visual asset on this site is drawn in code in this repository or generated by a
script in this repository. Nothing comes from an asset library, nothing is traced from
a photograph, and nothing carries a third-party licence except the three typeface
families, which are OFL and shipped with their licences.

## The pixel art

`src/assets/pixel/*.png`, drawn by `tools/pixel_art.py`.

```bash
python tools/pixel_art.py --out src/assets/pixel
```

No third-party module is involved — the script contains its own thirty-line PNG
writer. Shapes are built from pixel clusters on an explicit integer grid, diagonals are
stepped with Bresenham, shading is a handful of deliberate tones, and the only texture
is an ordered 4x4 dither. **Nothing here is a downscaled render or a pixelation
filter**; the earlier Blender model served only as a proportion reference and its
output is no longer part of the site.

| File | Grid | Dark | Light |
|---|---|---|---|
| `machine-{theme}.png` | 216 x 150 | 1021 B | 1016 B |
| `machine-compact-{theme}.png` | 120 x 126 | 605 B | 594 B |
| `wallpaper-{theme}.png` | 240 x 150 | 1087 B | 1086 B |

**Two framings, not one scaled down.** A 216-wide picture on a 390-wide phone can only
be shown at 1x before it runs off the screen, which leaves the tube far too small to
read. Narrow and short viewports therefore get their own composition — the monitor
alone, drawn larger on a smaller canvas — rather than a shrunken copy of the wide one.

**Two themes, one geometry.** The dark and light variants run the same drawing code
with different palettes. That is verified rather than asserted: the two images have
**zero alpha-coverage mismatches**, so they line up pixel for pixel and the screen sits
at identical coordinates in both. That is what lets the page swap themes without moving
anything.

**Outlines** are the design's hard rule: `#FFFFFF` on dark, `#000000` on light, one
grid unit thick, on the machine, the keyboard, the windows, the buttons and the
taskbar. The CSS palettes in `src/styles/tokens.css` mirror the palettes in the
generator, so a window border and the monitor's outline are the same value.

## How the live text is aligned

The monitor is drawn in an oblique projection whose depth runs back and to the LEFT,
which turns it to face slightly right: you see its left casing. The front face — and so
the tube — stays a true rectangle on the grid. That is deliberate: a sheared or
keystoned screen would resample the live text off the pixel grid and give it exactly
the uneven pixel widths this direction exists to avoid.

`tools/pixel_art.py` writes the tube's rectangle to `src/assets/pixel/pixel.json`, and
`build.mjs` turns it into the CSS custom properties the overlay uses — for both
framings — so no coordinate is ever copied by hand. The build refuses to continue if
the rectangle falls outside the artwork or stops being a tube shape.

The previous build asserted that the screen was axis-aligned. That was an assumption
about one particular asset rather than a real invariant, so it has been replaced: the
geometry is read from the asset, and an asset drawn in perspective would carry four
corners and take a matrix instead.

## Scaling

Raster pixel art is only ever shown at a **whole-number** multiple, chosen by
`src/scripts/room.js` from the viewport and re-chosen on resize and orientation change;
`image-rendering: pixelated` does the rest. The tests confirm the rendered box is
exactly the natural size times an integer at every viewport checked.

The room, the band on the inner pages, and all window chrome are CSS only — flat bands
with hard colour stops and checkerboard dithers built from `repeating-conic-gradient` —
so they are resolution-independent and need no asset at all.

## Fonts

See `src/assets/fonts/README.md`. Silkscreen carries the interface, VT323 the monitor,
and Karla is kept for running prose on the inner pages, where a bitmap face would hurt
readability at paragraph length. All three are SIL Open Font License 1.1, self-hosted
with their licence files.

## Superseded

`tools/model_crt.py` still builds the earlier photorealistic Blender render. It is kept
because it is a working script and a useful proportion reference, but nothing it
produces is part of the site any more and its output is not committed.
